# Uvicorn workers safety audit

Audit date: 2026-09-05. Platform: Windows, CPython 3.11 environment requested by the user, uvicorn 0.42.0. Scope: every backend launched by `demo.py`: SOC, Trading, Purchasing, DataOps, and S2P, including their shared scorer, graph, cache, control, and persistence paths. Existing uncommitted work was preserved; the change list below separates work already present at the start from changes made during this audit.

## Summary

**Verdict B for unrestricted mutable workflows: UNSAFE with N workers.** The launcher supports `--workers N`, stderr diagnostics, and bounded AGE pools, and five copilots can start with two spawned workers. That is not proof of learning correctness. `FreshScorerProxy` actually caches a scorer; persistent centroids and outcomes do not automatically refresh another worker's model, Welford accumulator, reinforcement-learning posterior, cache, or control state. This audit adds bounded file-write and startup protections and verifies existing SQLite/outbox protections. Completing cross-worker learning, control transitions, job ownership, and invalidation requires the larger designs below, deferred under the user's explicit **more than 200 new lines → design and flag for another prompt** rule. Multiple workers are suitable only for a constrained, quiescent dashboard experiment, not general demo/PW workflows that score, learn, reset, promote, transfer, or run live connectors. A blanket “SAFE with mitigations” or “0 new regressions” assertion is not justified by startup or dashboard tests.

## Critical Questions

**Q1 — Which SQLite file, and is WAL enabled?** The supplied paths `copilot_sdk/scoring/compounding.py` and `copilot_sdk/scoring/storage.py` do not exist in this checkout. Runtime code uses `scoring/scorer.py` and injected GraphStore implementations. The only separate legacy `DecisionStore` found is in sibling `compounding-scorer/compounding_scorer/storage.py:35`; it uses plain `sqlite3.connect` and is not the store imported by these five backends. Changing that unused class would not fix these applications. The active launcher explicitly selects AGE for all five (`demo.py:122`, `demo.py:232`). Development SQLite workers given the same absolute `db_path` share the same file, while `:memory:` is independent. Active `SQLiteGraphStore` already sets a 30-second busy timeout and WAL for file-backed stores and serializes schema migration with an OS file lock (`graph/sqlite_store.py:396`). WAL allows readers alongside a writer; there is still one writer and `SQLITE_BUSY` remains possible after a timeout or on some transaction upgrades. Busy timeout, not WAL alone, supplies bounded waiting. [SQLite WAL documentation](https://www.sqlite.org/wal.html), [busy timeout](https://www.sqlite.org/c3ref/busy_timeout.html).

**Q2 — Is centroid divergence acceptable for demo mode?** No for any demo that teaches, verifies or claims a common learned model. Centroids, DK state, phase and learning counters are in `CompoundingScorer`/`ProfileScorer` memory, initialized from store at construction (`scoring/scorer.py:319`, `:336`) and modified in `learn()` (`:1036`). A fixed, quiescent dashboard experiment can tolerate duplicated immutable runtime snapshots, subject to the limitations below. It is not a certification of live learning.

**Q3 — Is 5 × 4 = 20 PostgreSQL connections safe?** That calculation assumes one connection per worker, which is false here. `AGEClient` supports fresh-per-operation, pooled, and serialized warm-fallback modes (`ci-platform/ci_platform/graph/age_client.py:142`, `:202`). There can be multiple clients per backend, plus transaction/fresh connections and external tools. The launcher already narrows multiworker pools to min 1 / max 2 per client (`demo.py:1002`); the single-worker configuration retains max 15. A live query during the two-worker run observed `max_connections=100`, **44 total sessions** (34 idle, 5 active, 5 without a state, including the audit query and other activity). That is a point observation, not a four-worker capacity guarantee. Budget `sum(workers × client_instances × pool_max) + fresh/transaction peaks + other sessions + reserve < max_connections`. Two workers were exercised; four workers per copilot are not certified. No redundant connection pool was added.

**Q4 — Does preseed happen only before startup?** No. `scripts/preseed_all_copilots.py:4` explicitly operates against running backend HTTP APIs. Its scoring/learning loop is live mutation, not read-only fixture preparation. In addition, startup code can restore bundles/seed cold stores. Purchasing mtime caching only refreshes the fixture files it reads (`data_cache.py:22`); it cannot invalidate centroid, Welford, RL or tab caches. Prepare data using one worker, stop it, and start the requested workers after seeding is complete. Do not preseed during a multiworker run. Atomic fingerprint export now prevents partial JSON, but does not solve model coherence.

**Q5 — Does “Fresh” create a scorer/connection per request?** No. `_scorer_instance` is initialized once under an RLock and returned thereafter (`backend/scorer_proxy.py:33`). The graph store is made in the proxy constructor and borrowed by the scorer; `_close_scorer_store` is deliberately a no-op (`:176`). This avoids N×M scorer construction but causes stale model state. AGE's default fresh connection mode is separate from scorer lifetime; launcher pooling bounds client sessions, not all possible application resources. S2P/SOC own scorer state without this proxy.

**Q6 — Does write-through keep score and learn on different workers consistent?** The decision is written through to the shared store, so another worker can usually locate its ID (`scoring/scorer.py:391`, `:429`, `:933`). Persistence failures may be queued rather than immediately visible (`:435`, `:452`). Outcomes, receipts, checkpoints and L5 fields are also persisted (`scoring/scorer.py:1065`, `backend/scoring_router.py:309`). But there is no shared lock spanning reload → validate → update → commit of the entire learning state, and no committed model revision that refreshes every reader. Two workers can learn from stale centroids or overwrite Welford/posterior state. A router's double-verify check and its mutation lock are process-local (`backend/scoring_router.py:234`). Recreating a scorer alone also loses uncheckpointed batch/counter/control state and can race another writer; it is not a sufficient fix.

**Q7 — Are conservation counts local?** There are distinct paths. `compute_conservation_status_payload()` obtains counts from GraphStore methods (`backend/conservation_utils.py:261`, especially `:282`), so an uncached call reads committed shared counts. The conservation route is wrapped in `cached_static` (`backend/conservation_router.py:47`); a registered tab cache may retain a stale result. The learning gate also consumes the scorer's cached verified decisions (`scoring/scorer.py:2560`, `:2568`). Thus a fresh graph-backed status is better than an in-memory count, but it does not make the learning gate or all rendered panels consistent. Requiring one coherent conservation authority remains necessary; different answers solely because of worker selection are not acceptable for mutable demo workflows.

**Observed cross-process divergence:** a real two-process spawn probe used two cached FreshScorerProxy instances and one temporary SQLiteGraphStore database. Worker A learned one decision successfully, with centroid delta `0.012183498944759565`. Worker B then read the shared verified count as **1**, while its already-loaded verified-decision history remained **0** and its centroid distance from the committed store was **0.012183498944759565**. Thus a correct shared count does not establish a fresh model or learning gate. The probe used isolated temporary state and synthetic preseed context solely to exercise the actual learn path; it did not mutate the live demo or mock a scorer/store. Reproduction helper: `../.codex_tmp/workers_model_probe.py`; captured output: `logs/workers_model_probe.log`.

## Platform Concerns

**P1 — Spawn/import/startup.** Uvicorn uses spawn on Unix as well as Windows, unlike Gunicorn's prefork model. Each worker imports `app.main:app` and runs its own ASGI lifespan/startup; an app instance passed directly is unsuitable for multiprocessing. The three SDK apps call `create_app()` at module level; S2P builds its scorer at module import; SOC initializes learning state in lifespan startup. Their AGE clients are therefore created in each worker, not inherited connections. Added `demo/startup.py:13` locking serializes the P/T/D seed-check/write/restore sequence for a common local DB identity, including the direct-TestClient health path. It does not establish a global “one worker initialized the entire platform” flag, serialize SOC/S2P module-level migrations, or elect one owner for background jobs. [Uvicorn deployment](https://www.uvicorn.org/deployment/).

**P2 — Socket binding.** Uvicorn's parent binds a socket and passes it to spawned children. It does not require every Windows worker to bind the port using SO_REUSEPORT. The installed `uvicorn/_subprocess.py` uses `multiprocessing.get_context('spawn')`; `uvicorn/main.py` passes `config.bind_socket()` to the multiprocess supervisor; `uvicorn/server.py` shares sockets for Windows workers. Two startup-complete messages were observed for every one of the five backends in the two-worker run.

**P3 — Reload.** Installed uvicorn 0.42.0 warns that workers are ignored when reload is enabled; it does not reject the combination at argument parsing. Uvicorn's entrypoint selects reload before the multiprocess branch. `demo.py` resolves the conflict explicitly: warn, drop reload, retain the requested workers. Default workers=1 does not append `--workers`; explicit `--reload` remains available for that mode. [Uvicorn settings](https://www.uvicorn.org/settings/).

**P4 — Stop.** Killing only a child lets the supervisor restart it. Killing only a parent with ordinary process termination is not a Windows process-tree cleanup guarantee. The launcher discovers exact TCP LISTENING local ports and uses `taskkill /F /T /PID` (`demo.py:667`, `:703`). It handles multiple listeners/IPv4/IPv6 and uses the tree flag; verification must check all recorded server/supervisor PIDs in addition to ConnectionRefused. The Unix branch uses Windows-oriented netstat parsing and plain `os.kill(pid, 9)`; it is **not certified for Unix tree cleanup by this Windows audit**.

## Verdict + Mitigations Applied

Nine risk classes were identified: **R1** learning/model transactions, **R2** mutable control/session authority, **R3** cross-worker cache invalidation, **R4** shared file updates, **R5** startup/background ownership, **R6** outbox duplicate processing, **R7** connection multiplication, **R8** SQLite writer/schema contention, **R9** multi-operation graph races. Several are risks already present with multiple threads; multiple processes remove the protection offered by existing Python locks.

Five bounded mitigation groups are present in the resulting checkout:

1. **SQLite and outbox coordination (existing work reviewed and verified):** WAL, bounded busy timeout, schema locks and cooperating-process drain/replay/dispatch locks. These serialize database operations/batches, with crash-time idempotency still required. Never delete a lock file while workers may hold it; OS lock release, not file deletion, controls ownership.
2. **Fixture/file publication:** existing Purchasing deep-copy/mtime cache and metadata locking retained. Added shared atomic JSON publication for fingerprint exports and Trading metadata; Trading metadata and journal RMW now hold a file lock across read/update/replace. These are local-filesystem, cooperating-writer guarantees, not network-filesystem/distributed locks. Trading promotion JSON and other runtime control files still need the larger control-state design.
3. **P/T/D startup serialization:** lock the whole seed check/write/restore sequence, so two fresh processes cannot both observe an empty store and restore the same checkpoint batch. Both in-memory tests and workers=1 remain supported. The lock key is the normalized scoring DB path; processes pointing at the same AGE graph through different local DB identities are not coordinated by this key. Startup registration before this section and external preseeding remain separate concerns.
4. **Connection budget:** preserve existing AGE reuse/pooling; multiworker launcher pools are bounded at 1–2 connections per client. Actual session count was measured. No promise is made for an arbitrary N; budget headroom must be checked.
5. **Launcher diagnostics and worker configuration:** positive integer `--workers` default 1; reload warning; per-start logs; last 20 lines on failed health; hints for ImportError/ModuleNotFoundError, KeyError, address-in-use, GRAPH_DSN and refused connections. This audit extends pattern detection to the whole log while keeping displayed output bounded, so worker-restart noise cannot erase the hint. Existing launcher tests now isolate both log and keepalive paths rather than overwriting live diagnostics/PID files.

**Verdict A — limited experiment only:** workers=2 is usable for a Purchasing dashboard test against already prepared, stable data; all workers must finish initialization; no live score/learn/preseed/reset/transfer/promotion/import/perturbation operations, mutable demo job sessions, or enabled background ingestion may run; data must be refreshed by a full restart after mutation; pool/session budget must fit; the audited endpoint set must tolerate duplicate read-triggered artifact persistence. This is an operational restriction, not an HTTP write guard. A request being GET is not proof of no side effects: fingerprint/trajectory paths may persist artifacts and SOC/S2P warmup can write graph state.

**Verdict B — normal interactive demos and mutation-heavy PW suites:** unsafe until the designs below are implemented and proven. **Verdict C applies only to the bounded file/store operations just verified**, not to the whole application. The launcher visibly warns operators to use workers=1 for writes. It does not silently reduce N or pretend to enforce read-only mode.

### Separate prompt: coherent learning and invalidation (estimated >400 new lines)

Introduce a backend-neutral transaction boundary keyed by store identity, tenant and domain. PostgreSQL uses a stable advisory lock plus a transaction; local SQLite uses BEGIN IMMEDIATE and cooperating process/thread locking. Under that boundary, load a **complete versioned runtime snapshot** (centroids, DK, Welford means/M2/counts, phase/decision count, tau, conservation pause/baseline, RL posteriors, batch state and schema hash), reject duplicate/conflicting outcome IDs, update, and atomically commit outcome + model state + evidence/outbox + a monotonically increasing revision. Publish no successful new model revision on partial persistence failure. In-memory state must revert or reload after failure. Every read and write, including proxy unwrapping, direct S2P/SOC scorers, checkpoint rollback, transfer and regime reinitialization, must participate.

Use that revision to invalidate scorer and TabStateCache/DI/financial/factor snapshots across processes. Cache keys include store identity, tenant, domain and revision. Read a coherent snapshot rather than several unrelated graph counts. LISTEN/NOTIFY can accelerate invalidation but cannot be its only durable signal. Retain separate immutable fixture caches. Avoid restoring only L5 centroid vectors: that omits several state fields listed above.

Blast radius: SDK scorer/proxy/router/state/GraphStore protocol + SQLite and AGE adapters, GAE runtime serialization, P/T/D wiring, and both SOC/S2P bridges; more than five files and multiple repositories. Acceptance: two-worker alternating learn/score matches a serial reference; simultaneous distinct learns retain both updates; duplicate learns commit once; readers see one committed revision; kill writer before/after commit; restart both; test rollback, transfer, conservation and tenants. No scorer/store/conservation test doubles.

### Separate prompt: control state, jobs, files and graph upserts (estimated >300 new lines)

Persist and transactionally version auto-order/promotion/regime/perturbation/frozen-twin state, imported trades, webhook histories, novelty/receipt chains and SOC feedback/reset state. Replace mutable-reference `get()` APIs with transactional update operations; a file lock around only `save()` still writes stale cached state. Persist job IDs/status/cancellation and elect one background poller owner with a renewable lease and durable ingestion idempotency. Put graph check-then-create/upsert and chain-tip allocation under database-scoped locks/unique identities, with crash/retry tests. Coordinate startup bootstrap and schema work separately from per-worker resource initialization. Update every remaining JSON writer to the same atomic+RMW protocol or migrate it to the shared store. Add process-wide resource shutdown for all owned stores/pools/executors; workers should not close another component's borrowed store.

These are concrete deferred designs under the requested code-size limit, not claims that the current worker warning makes mutation safe. SOC/S2P receipt/job/control behavior is why a small FreshScorerProxy-only patch would be misleading.
